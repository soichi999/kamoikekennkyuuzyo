# CLAUDE.md — カケコミ 危険度スコア分析

**このディレクトリは `/apps/data`。** モノレポの一部であり、分析専用の作業領域。

- 作業対象は `/apps/data` 配下のみ。**他の `apps/` を触らないこと**
- ファイルパスはすべて `/apps/data` からの相対パスで書く
- AIツール（Claude Code / OpenCode）で作業することを前提とする。作業前に必ずこのファイルを読むこと
- 各フェーズごと、データを整理し、テーブルを作ったなら、processedにも保存を忘れないこと

---

## 1. このディレクトリの目的

**`real.js` に貼る係数を1つ出すこと。** それだけ。

分析レポートを書くことでも、きれいな可視化を作ることでもない。
最終成果物は Phase 6 で出力する係数JSON。

---

## 2. プロジェクト背景

**カケコミ** = 子どもが「助けて」と駆け込める場所の密度をスコア化するアプリ。
都知事杯オープンデータ・ハッカソン2026 提出作品。チーム名「鴨池研究所」。

- バックエンド（Cloudflare Workers）は別リポジトリで **実装完了済み**
- スコア計算だけが `src/scoring/` に分離されており、そこに入れる係数を作るのがこのリポジトリ
- iOS アプリは相方が担当

### なぜ回帰分析をするのか

不審者情報（メールけいしちょう）には **報告バイアス** がある。
そのまま地図に載せると「報告が多い場所 = 危険」になってしまい、実態とズレる。

そこで **環境要因（駆け込み先の密度）から危険度を推定する式** を作り、
報告バイアスを統計的に分離する。

## 3. データ

| データ                                     | 単位     | 用途            |
| ------------------------------------------ | -------- | --------------- |
| 不審者・声かけ事案（メールけいしちょう）   | 町丁目   | 目的変数        |
| 町丁目境界 `r2ka13.shp`（令和2年国勢調査） | ポリゴン | 集計の器 + 人口 |
| 交番・駐在所（警察庁）                     | 点       | 説明変数        |
| 学校                                       | 点       | 説明変数        |
| コンビニ（OSM）                            | 点       | 説明変数        |

### こども110番の家について

**使わない。** 位置情報が都全域でオープンデータ化されていないため。
これは欠点ではなく、**プレゼンで「データ整備の必要性」を訴える材料** として使う。
勝手に代替データを探したり、推定で補完したりしないこと。

### 既知の性質

- 事件データは **「不審者・声かけ」に絞った状態** で使う。電話詐欺・特殊詐欺は除外済み
    - 荒川区は **72件**（96件なら絞り込み前なので要確認）
    - 丁目レベルの行のみ使用。全体で約2,308件
- `r2ka13.shp` は **DBFがShift-JIS**。`encoding="cp932"` を指定しないと文字化けする
- `r2ka13.shp` の座標系は **JGD2000 平面直角座標系第9系（メートル単位）**
- `S_NAME` は漢数字（`南千住四丁目`）、事件データは分割形式（`南千住` + `4丁目`）

### Phase 0 で判明したこと（棚卸し済み）

| データ       | 件数                 | 緯度経度            | 状態                                       |
| ------------ | -------------------- | ------------------- | ------------------------------------------ |
| 事件データ   | 21,253               | —                   | 絞り込み前。特殊詐欺 15,263件（71.8%）混入 |
| 町丁目境界   | 6,021                | polygon (EPSG:2451) | OK                                         |
| 交番・駐在所 | 688（23区）          | **無し**            | ジオコーディング必要                       |
| 学校         | 1,884（4ファイル計） | **無し**            | ジオコーディング必要                       |
| コンビニ     | 5,500                | **無し**            | OSMから取り直す                            |

**① 緯度経度が無い（最大の作業）**

- コンビニは **OSM から取り直す**。Overpass API は座標付きで返るのでジオコーディング不要
    ```
    [out:json][timeout:180];
    node["shop"="convenience"](35.50,139.55,35.85,139.95);
    out body;
    ```
- 交番（688件）と学校（約1,200件）は **国土地理院API** でジオコーディングする
  `https://msearch.gsi.go.jp/address-search/AddressSearch?q={住所}`
  無料・登録不要。リクエスト間に 0.2〜0.5秒 のウェイトを入れる
- ⚠️ レスポンスの `coordinates` は **[経度, 緯度]** の順。取り違えると座標が海外に飛ぶ
- 結果は `data/processed/koban_geocoded.csv` / `school_geocoded.csv` に保存
- **成功率が 90% を下回ったら止まって報告する**

**② 住所に都道府県・区名が無い行がある（静かに壊れる罠）**

住所は `千代田区一ツ橋` のような区名始まりと、`麹町2-8` のような町名始まりが混在している。

⚠️ **区名を補完せずにクエリを投げると、別の区の同名町にヒットして座標が静かに壊れる。**
エラーが出ないため発見が遅れる。必ず以下の手順を踏むこと。

1. 住所のサンプル20件を表示してパターンを確認する
2. 23区名リストとの前方一致で、区名始まりかを判定する
3. 区名が無い行は補完する
    - 学校: `設置者` 列の自治体名、それが無ければ `郵便番号` から特定
    - 交番: `市区町村` 列があるのでそれを使う
    - どちらも不可なら「区不明」として保留し、件数を報告する。**推測で埋めないこと**
4. 最終的なクエリは必ず `"東京都" + "○○区" + "町名以降"` の形にする
5. **検証**: 取得座標を町丁目ポリゴン（`r2ka13`）に空間結合し、
   元データの区名と一致しない件数を報告する。ここで誤爆が全て検出できる

**③ 学校は4ファイルのみ使う**

| ファイル                             | 件数  | 使う            |
| ------------------------------------ | ----- | --------------- |
| `shougakkou-address_4.csv`           | 1,262 | ✅ 小学校       |
| `chuugakkou-address_3.csv`           | 608   | ✅ 中学校       |
| `gimu-address_3.csv`                 | 8     | ✅ 義務教育学校 |
| `chuutou-address_3.csv`              | 6     | ✅ 中等教育学校 |
| `koutougakkou-ichiran-address_2.csv` | 186   | ❌ 高校         |
| `youchien-address_4.csv`             | 158   | ❌ 幼稚園       |
| `tokubetsushien-address_3.csv`       | 80    | ❌ 特別支援学校 |

除外理由: カケコミの対象は **一人で登下校する小中学生**。高校・幼稚園・特別支援は想定しない。

4ファイルは全て `encoding="cp932"`。`chuutou-address_3.csv` には空列が2つあるので、
必要な列（`学校名`, `住所`, `設置者`）だけを選んで `school_type` を付けて結合すること。

**④ その他**

- 町丁目境界の CRS は **EPSG:2451**（平面直角第9系・メートル単位）。
  ジオコーディングで得た緯度経度（EPSG:4326）を 2451 に変換してから結合・距離計算する
- `JINKO` が 0 の町丁目が 6,021件中 **610件**。除外する。23区内での件数も報告すること
- 事件データの住所空白 2,174件。絞り込み後に何件残るか確認する

## 4. 設計判断（変更しないこと）

以下は壁打ちで決定済み。**理由なく変えないこと。** 変えたい場合は先に相談。

### 学習と検証を分ける

- **学習: 23区のうち荒川区を除く22区**（約1,599件・町丁目約3,000）
- **検証: 荒川区**（72件・町丁目52）
- **多摩地域は除外**（丁目レベル比率が低く、町丁目の構造も23区と異なる）

学習に使っていない区で当てることが、精度の証明になる。

### ポアソン回帰を使う

```
件数 ~ Poisson(λ)
log(λ) = offset(log 人口) + β1×交番数 + β2×学校数 + β3×コンビニ数 + 区ダミー
```

- **人口を offset に入れる** → 「人あたり発生率」がモデル内で扱われ、分母問題が解決する
- **区ダミーを入れる** → 報告バイアスをここに吸収させる
- **予測時は区ダミーを使わない** → バイアスを除いた環境由来の危険度が得られる

ロジスティック回帰（あり/なし）にしないこと。件数情報を捨てることになる。

### 区ダミーが吸収する2種類のバイアス

このデータには報告バイアスが2層ある。どちらも区ごとの倍率なので同時に吸収できる。

1. **件数のバイアス**: 人口あたり件数が自治体間で最大9倍の差
2. **住所の詳しさのバイアス**: 丁目まで記載される率が港区6.2%・武蔵村山3.2%に対し、葛飾45.4%・足立43%と7倍以上の差

### 施設は300mバッファを取る

町丁目ポリゴン内 **+ 境界から300m以内** の施設を数える。

理由: 隣接町丁目にある交番も駆け込み先として機能する。
町丁目内だけで数えると、小さい区画がすべて0になり式が壊れる。

### 距離計算は平面直角座標系のまま行う

第9系はすでにメートル単位なので、300mバッファはそのまま `300` で計算できる。
緯度経度に変換してから距離を測らないこと。

WGS84 への変換は、GeoJSON 出力など **表示用途のときだけ** 行う。

### 学習は町丁目、適用は25mグリッド

- 事件データの粒度が町丁目なので、**学習は町丁目単位**
- 係数が出れば適用側は細かくできるので、**サービスでは25mグリッド**
- このリポジトリでは **25mグリッドは作らない**。町丁目までで完結する

## 5. フェーズ

**1フェーズずつ、以下のループを回すこと。**

1. 実装する
2. 実行する
3. **結果を報告する**
4. **`/docs` にそのフェーズの記録を書き、コミットする**
5. 完了条件を満たしていれば、**許可を待たずに次のフェーズへ進む**

許可を求めて止まらなくてよい。ただし以下の場合は **必ず止まって報告する**:

- 完了条件を満たせなかったとき
- Phase 2 の結合率が 80% を下回ったとき
- 設計判断（第4章）を変える必要が出たとき
- データが不足していると判明したとき

**「止まる」とは、回避策を実装せずに報告して待つこと。**
勝手に代替手段を実装して進まないこと。

| Phase | 内容                      | 完了条件                  |
| ----- | ------------------------- | ------------------------- |
| 0     | データ棚卸し              | 5データの状態表が出る     |
| 1     | 環境構築                  | import が全部通る         |
| 2     | 事件データ → 町丁目に結合 | 結合率が出る              |
| 3     | 施設 → 町丁目に空間結合   | 集計表（約3,000行）が完成 |
| 4     | ポアソン回帰              | 係数が出る                |
| 5     | 検証（荒川区）            | 3指標が出る               |
| 6     | 係数JSON出力              | `real.js` に貼れる形      |

### 各フェーズの完了条件（詳細）

**Phase 0** — 加工禁止。読み込んで報告するだけ。
問題を見つけても直さずに報告する。

**Phase 1** — `pandas` `geopandas` `shapely` `pyproj` `statsmodels` が import できる。
geopandas が入らない場合は `pyogrio` を先に入れる。

**Phase 2** — 住所の正規化（漢数字↔アラビア数字、`丁目` の有無、全角半角）。
**結合率を必ず表示する。** 80%を下回る場合は、一致しなかった住所を20件表示して原因を報告し、**そこで止まる**。

**Phase 3** — 出力は町丁目ごとの1行1レコード:

```
KEY_CODE, CITY_NAME, S_NAME, JINKO, koban_n, school_n, conveni_n, incidents
```

人口0の町丁目は除外し、除外件数を報告する。
各列の基本統計（平均・最大・0の個数）を報告する。

**Phase 4** — 係数・標準誤差・p値の表を出す。
符号が直感と逆の変数があれば指摘する（例: 交番が多いほど危険と出た場合）。

**Phase 5** — 荒川区は72件と少なくノイズが乗るため、以下3つを併記する:

1. Spearman順位相関（予測値 vs 実件数）
2. Top-N一致率（予測上位10町丁目のうち、実件数上位10に入っている数）
3. **3分位の単調性**（予測値で3群に分け、群ごとの平均実件数。低<中<高なら成功）

3が最も説明しやすいので、プレゼン用に必ず出す。

**Phase 6** — 以下の形式で出力:

```json
{
    "model": "poisson",
    "trained_on": "23区（荒川区を除く22区）",
    "validated_on": "荒川区",
    "spearman": 0.0,
    "top10_overlap": 0,
    "tercile_mean_counts": [0.0, 0.0, 0.0],
    "coefficients": {
        "intercept": 0.0,
        "koban_n": 0.0,
        "school_n": 0.0,
        "conveni_n": 0.0
    },
    "score_range": { "min": 0.0, "max": 0.0 }
}
```

加えて **盲点リスト**（予測値が高いのに実件数が0の町丁目 上位10件）を出す。
「危険なのに報告されていない場所」= アプリの提供価値そのもの。プレゼンで使う。

## 6. 作業ルール

- **フェーズをまたいでまとめて実装しないこと**
- **失敗や不足は隠さず報告すること。** 回避策を勝手に実装するより、報告して止まるほうが良い
- **データを加工したら、加工前後の件数を必ず出すこと**
- 中間ファイルは `data/interim/`、最終成果物は `output/` に置く
- 生データ（`data/raw/`）は書き換えない

### 数字を報告するときは必ず件数を添える

「結合できました」ではなく「2,308件中2,290件（99.2%）が結合できました」と書く。
率だけでも件数だけでも不十分。

## 8. ドキュメント

**各フェーズが終わるたびに `/docs/phaseN_<内容>.md` を作成し、コミットする。**

記録に含めるもの:

- 作成者名
- 使用したAIモデル
- タイムスタンプ
- **やったこと**（何を実装し、何を実行したか）
- **数字**（件数・率・統計量。「結合できた」ではなく「2,290/2,308件・99.2%」）
- **詰まった点と、どう解決したか**
- **次フェーズへの申し送り**（想定外の値、注意点）

大きな変更だけでなく、小さな修正も記録する。あとで発表資料の材料になる。

コミットメッセージは `docs: phase3 施設の空間結合` のように、
フェーズ番号と内容がわかる形にする。

このファイル（CLAUDE.md）も進行に合わせて更新していく。
設計判断が変わった場合は、第4章を必ず書き換えること。
